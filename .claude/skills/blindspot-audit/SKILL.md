# 盲区审查（Blindspot Audit）

## 这个 Skill 解决什么

自动化测试只覆盖它设计覆盖的东西；工程验证（typecheck / build / 单测）只证明语法与类型合法。
这两个都不证明应用在真实使用下行为正确。最常见的一类回归——
"导航点击不响应"、"状态切换不刷新"、"权限边界静默放行"——
都发生在测试未触及的代码路径上，而且没有任何自动化信号能预警。
本 Skill 的全部价值是把"我相信测试都过了"拆解成
"测试具体覆盖了什么、没覆盖什么"，让未触及的面变成可被看见、
可被决定是否补测的对象。

## 何时调用

- 刚跑完一次重构（架构调整、配置迁移、API 适配更换），即将宣告完成
- 在生产或手动走查中发现了你自己没发现过的 Bug
- 准备发布前的最终验收
- 接手陌生代码库第一次写代码之前（建立基线）
- 用户在问你"为什么这个 Bug 你没发现"——用本 Skill 把失败模式写下来，编码成下次能用的清单

**不要**用来实现功能或写代码。本 Skill 只做审查与报告，不动手实现。

## 操作步骤

### 1. 重建接触面清单

列出你**实际读过、改过、跑过**的代码路径。然后列出项目里**所有同类的、但你没动过的**路径。
两者的差就是盲区。

例子：
- SPA：每个导航项、每个按钮、每个模态触发器、每个表单提交。我改过 X，没动过 Y、Z。
- API：每个路由、每个中间件、每个状态分支。
- 状态机：每种状态的合法组合（空 / 加载中 / 错误 / 过期 / 多用户 / 并发）。

### 2. 状态组合矩阵

对每个交互入口，列出关键状态维度并勾选覆盖情况：

| 状态维度 \ 入口 | 入口 A | 入口 B | 入口 C |
|---|---|---|---|
| 无数据 |  |  |  |
| 加载中 |  |  |  |
| 错误（404 / 5xx / 网络断开） |  |  |  |
| 数据过期 / 缓存失效 |  |  |  |
| 权限不足 / 未登录 |  |  |  |
| 并发 / 重复点击 |  |  |  |

未勾选的就是未验证。常见未勾选项是"错误"和"无数据"——bug 高发区。

### 3. 基线对比（重构 / 迁移专有）

列出重构**之前**应用能做到的事，逐条验证重构后是否仍然可用：

| 重构前能做的事 | 重构后状态 | 备注 |
|---|---|---|
| 点侧栏切换视图 | 仍可用 / 已破坏 / 不再适用 | 理由 |

不能跳过这步——它把"测试过了"翻译成"用户能做的事没变"。

### 4. 手动走查

把 1–3 的结论翻译成可以手动点击的清单，在浏览器里（或用 e2e 脚本）
**实际走一遍**。每条点过、看过、确认过。工程验证不能替代这一步——
这是发现的唯一步骤。

### 5. 发现 → 补测 / 修复

把走查中发现的问题分两类：
- **行为错误**：功能坏了。修复 + 加自动化回归测试（e2e 或单元），
  让同样的失败模式以后会被自动化捕获。
- **空白覆盖**：行为正确但没有测试。补一个最小回归测试，
  防止以后重构时再次漏掉。

### 6. 输出报告

给作者一段简短的审查报告：
- 列已审计（带证据）
- 列未审计（附理由为什么可以跳过）
- 列发现的问题与优先级

把报告附在 PR 描述或 commit message 里，作为这次工作的可追溯记录。

## 反模式

- 看到 `pnpm test` 全绿就宣称"完成"。测试套件不等于覆盖率。
- 重构后只 spot-check 一两个交互就觉得够了。
- 用"测试覆盖"的代码路径证明"未触及的面不存在"——循环论证。
- 把盲区报告做成套话格式（永远"经审查未发现新盲区"），而不是真的去找。

## 当你因为没发现 Bug 而被问到

诚实回答三个问题，写进这次修复的回归测试和下次审查的清单——这就是"经验"而不是"教训"：

1. 这个 Bug 在我读 / 改 / 跑过的代码里吗？（答：在哪个集合？没在 = 盲区 = 列进下次清单）
2. 我当时在做什么？这个 Bug 类型的检查在当时流程的哪一步被遗漏了？
3. 这次失败的具体模式是什么？（重构隧道视野 / 状态分支未走 / 入口未点 / 基线遗漏 / 其他）

把这三个答案编码成下一步：补哪个回归测试（自动化）+ 哪条手动检查清单（流程）。
